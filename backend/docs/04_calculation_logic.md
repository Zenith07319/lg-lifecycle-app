모든 비교는 **5년(여름 3개월 × 5년 = 15개월)** 기준으로 산정한다.

## 1단계: 상태 진단 지표

### 1-1. 점검 필요도 (0~1)

> "고장 확률"이 아닌 입력 조건 기반 점검 필요도 점수화. "예측"이라는 표현 사용 금지.

**가중치 구성 (v2 — 코드 기준)**

| 요소 | 가중치 | 계산 방법 |
|------|--------|---------|
| 연식 | 0.30 | min(사용연수 / 기대수명, 1.0) |
| 증상 심각도 | 0.30 | 증상_기본값 × 심각도_배율 |
| 수리 이력 | 0.15 | min(수리 횟수 × 0.33, 1.0) |
| 관리 미이행 | 0.15 | min(필터_미청소_월수 × 0.10, 1.0) |
| VOC 위험도 | 0.10 | 동일 증상 소셜 빈도 기반 (0~1) |

> **[확정: 점검 가중치 = 수리이력 0.15 / 관리미이행 0.15]** (2026-06-03 확정) 코드 `src/calculations_v2.py` `calculate_inspection_score` 값을 정본으로 한다. 구버전 문서·docstring의 '0.20 / 0.10' 표기는 폐기한다. (합계 연식 0.30 + 증상 0.30 + 0.15 + 0.15 + VOC 0.10 = 1.00)

```
inspection_score =
  연식점수 × 0.30
  + 증상기본값 × 심각도배율 × 0.30
  + min(수리횟수 × 0.33, 1.0) × 0.15
  + min(필터미청소월 × 0.10, 1.0) × 0.15
  + VOC위험도 × 0.10
```

**제품별 기대수명**

연식점수의 분모(노후 점수가 1.0으로 포화되는 기준 연수)다. **"수명이 다하는 시점/고장 예측이 아니라"**, 연식을 0~1로 정규화하는 기준값이다.

|------|---------|------|

| 건조기 | 12년 | 공학적 기대수명(AS법·업계) |

> **에어컨 16.7년 — 출처 및 계산법** (2026-06-04 변경, 구 15년)
> - **출처**: KESIS 가구에너지패널조사(HEPS) 13차(2022년 기준) 마이크로데이터(`HEPS13_micro_app`, 변수 `s13_601_106` 에어컨 신규구매 여부, 가구가중치 `cwgt22_hh`).
> - **계산법(역산)**:
>   ```
>   보유가구 기준 신규구매율(%) = Σ(신규구매 가구 가중치) / Σ(보유가구 가중치)
>   단순 역산 구매주기(년)      = 100 / 평균 신규구매율(%)

>   에어컨 연도별 신규구매율: 2019 4.97% / 2020 8.30% / 2021 5.98% / 2022 4.71% → **평균 5.99%**

> - **한계(명시)**: ① 단순 역산은 신규구매에 *첫구매·추가구매(보유가구당 1.18대)*가 섞여 실제 교체수명과 다를 수 있음. 보급률(92.1%)로 첫구매를 보정하면 16.7÷0.92 ≈ 18.2년으로 더 길어짐. ② 동일 방식의 냉장고(28.9년)·세탁기(27.5년)는 과대 추정이라 **에어컨에만 적용**하고 타 제품군은 공학값 유지. ③ "평균 사용기간"이며 개별 기기 고장시점 예측이 아님.

**증상 심각도 1~5점 척도 (배율)**

증상 심각도는 4단계(없음/낮음/중간/높음)에서 **1~5점 척도**로 확정 변경되었다. (PROJECT.md §8-2)

| 심각도(점) | 의미 | 배율 |
|--------|------|------|
| 1점 | 없음/거의 없음 | 0.1 |
| 2점 | 낮음 | 0.6 |
| 3점 | 중간 | 1.0 |
| 4점 | 높음 | 1.4 |
| 5점 | 매우 높음 | 1.8 |

> **[검토 필요: 심각도 5점 배율 — 5점 배율값 TBD]** 현재 코드 `src/calculations_v2.py` `SEVERITY_MULTIPLIER`는 아직 4단계 매핑 `{없음:0.1, 낮음:0.6, 중간:1.0, 높음:1.4}`로 유지되어 있다(5점 척도 마이그레이션은 PROJECT.md §8-4의 '명시적 지시 시 진행' 대상). 위 표의 1~4점 배율은 기존 코드값(0.1/0.6/1.0/1.4)을 그대로 1~4점에 대응시킨 것이며, **5점(매우 높음) 배율 1.8은 잠정값**이다. 코드 마이그레이션 시 5점 배율을 확정해야 한다.

### 1-3. 에너지 낭비

```
낭비 kWh = max(구형_연간_kWh - 신형_연간_kWh, 0)
낭비 비율 = 낭비 kWh / 신형_연간_kWh
```

**에어컨 월 소비전력 추정 (효율관리제도 '표준 월간 소비전력량' 기반)** — 2026-06-04 변경

베이스를 `연간_kWh / 12`(파생값)에서 **에너지소비효율등급 라벨의 '표준 월간 소비전력량'(kWh/월) 직접 사용**으로 변경했다. 이 값이 라벨에 표기되는 1차 데이터이기 때문이다.

```
K_AC_월(신품 기준) = 표준_월간_kWh × (실제_사용시간 / 기준_사용시간(7.8h))
실제 K_AC_월       = K_AC_월(신품 기준) ÷ 잔존효율 η     (구형만 η<1)
```

- **기준 사용시간 = 7.8h/일** (구버전 8h에서 정정). 근거: 효율관리제도 냉방기간 표준 = **4개월(6~9월) × 941시간 운전** → `941h ÷ 4개월 ÷ 30일 ≈ 7.8h/일`.
- 라벨 월간값은 이 941시간을 **월별·오전/오후 실외온도(24~38℃) 분포로 가중**해 산출된 값이다. 즉 표준 온도분포를 이미 내포한다.
- ⚠ **한계(온도 비선형)**: 실제 소비전력은 실외온도가 높을수록 급증(비선형)한다. 본 식은 라벨 월간값이 표준 온도분포를 내포한다는 전제 하에 **사용시간 선형 보정**으로 근사하므로, 표준 대비 사용 패턴이 크게 다른 경우 오차가 있다. (정밀화는 온도구간별 가중 모델 필요 — 확장 과제)
- **K_AC 베이스 입력 우선순위**: ① 사용자가 진단 시 **에어컨 라벨의 월간소비전력량을 직접 입력**(`ac_monthly_kwh_input>0`)하면 그 값을 구형 베이스로 사용(가장 정확) → ② 미입력 시에만 `data/device_energy_spec.csv`의 `monthly_kwh`를 **용량+연식으로 조회**한 표 추정값으로 폴백(최후 수단). 입력값은 라벨 '신품 정격값'이므로 잔존효율 η로 연식 열화를 반영하고, `annual_kwh = 입력값 × 12`.
- **전력 계산은 용량(kW)과 무관**: 신형(1등급 고효율) 비교값을 용량표가 아니라 **구형 라벨값 × 효율비(`NEW_EFF_RATIO=0.70`)** 로 도출한다(효율관리제도 신고스펙상 1등급/3등급 구형 평균비 0.67~0.73 → 0.70). 따라서 **전력(에너지)은 오직 월간소비전력량으로 계산되어 용량과 무관·연속**이며, **용량은 비용(수리/구매/구독)·제품추천 조회 키로만** 쓰인다(이산/근사로 충분). [한계] 구형이 이미 1등급이면 절감폭 과대평가(상수 비율 근사).
- **데이터**: `data/device_energy_spec.csv` `monthly_kwh` 컬럼. 라벨 미확보 모델에 한해 `annual_kwh ÷ 12` placeholder. (에너지 낭비 비율 §1-3 상단은 `annual_kwh` 기준 유지)

출처: 한국에너지공단 효율관리제도 표준 월간 소비전력량 (`src/tariff_calculator.py` `calc_ac_monthly_kwh`, `REFERENCE_DAILY_HOURS=7.8`)

### 1-4. 가전 건강등급 (A~E)

```
종합위험 = 점검필요도 × 0.45 + 에너지낭비비율 × 0.30 + 생활불편도 × 0.25
건강점수 = 100 - 종합위험 × 100

| 점수 | 등급 | 의미 |

## 2단계: 전기요금 계산

### 에어컨 기여 델타 방식 (v2 핵심 변경)

> 가구 전체 요금이 아닌, 에어컨이 **추가함으로써 발생하는 요금 차액**만 사용한다.

```
K_AC_델타 = Bill(K_기준 + K_AC) - Bill(K_기준)
```

- K_기준: 에어컨 미사용 시 가구 기준 월 소비량
- K_AC: 에어컨 월 소비량

### 기본 공식

```
월 청구액 = 기본요금 + 전력량요금합계 + 기후환경요금 + 연료비조정요금
           + 부가세(10%) + 전력산업기반기금(3.7%)
```

기후환경요금: 9.0원/kWh  
연료비조정요금: 5.0원/kWh  
기준일: 2025년 4월 1일 시행 전기요금표

### 하계 주택용전력 고압 (아파트 기본값)

| 구간 | 기본요금 | 전력량요금 |
|------|----------|-----------|
| 300kWh 이하 | 730원 | 105.0원/kWh |
| 301~450kWh | 1,260원 | 174.0원/kWh |
| 450kWh 초과 | 6,060원 | 242.3원/kWh |

### 하계 주택용전력 저압 (원룸·빌라 등 개별 고지)

| 구간 | 기본요금 | 전력량요금 |
|------|----------|-----------|
| 300kWh 이하 | 910원 | 120.0원/kWh |
| 301~450kWh | 1,600원 | 214.6원/kWh |
| 450kWh 초과 | 7,300원 | 307.3원/kWh |

### 누진구간 비교 핵심

단순 kWh 절감보다 **누진구간 이동** 여부가 더 큰 차이를 만든다.

```
예시 (4인 가구 / 아파트 / 하계):
기준 350kWh + 구형 AC 110kWh = 460kWh → 고압 3구간 (기본요금 6,060원)
기준 350kWh + 신형 AC 80kWh  = 430kWh → 고압 2구간 (기본요금 1,260원)

AC 기여 델타:
  구형 AC: Bill(460) - Bill(350) = 64,693원/월
  신형 AC: Bill(430) - Bill(350) = 17,101원/월
  교체 시 월 절감: 47,592원
  5년 절감: 47,592 × 15개월 = 713,880원
    (월 절감 47,592원 × 여름 3개월 × 5년 = 47,592 × 15 = 713,880원)
```

> 비교기간이 3년 → 5년으로 변경되어 절감 누계는 9개월분(428,328원)에서 **15개월분(713,880원)**으로 갱신됐다.
> 위 절감액은 연도별 효율감퇴를 반영하지 않은 단순 누계다. 실제 파이프라인(`app/backend/app/services/calculation.py`)은 연도별 잔존효율을 적용한 5년 누계를 사용하므로 값이 더 낮아질 수 있다.

## 3단계: 선택지별 에어컨 관련 5년 총비용 (델타 방식)

| 선택지 | 비용 구성 |
|--------|----------|
| ① 계속 사용 | 전기비_5년(구형) |
| ② 셀프케어 | 전기비_5년(구형) + 셀프케어비 × 5 |
| ③ 수리 후 사용 | 전기비_5년(구형) + 수리비 + 출장비 |
| ④ 구독 전환 | 구독료 × 60개월 + 전기비_5년(신형) |
| ⑤ 신제품 구매 | 구매가 + 전기비_5년(신형) |

> 위 산식은 실제 파이프라인 `app/backend/app/services/calculation.py`의 선택지별 5년 비용 덮어쓰기 로직과 일치시킨 것이다.
> - 계속사용 = `elec_5yr["계속사용"]`
> - 셀프케어 = `elec_5yr["셀프케어"] + selfcare_mid × 5`
> - 수리후사용 = `elec_5yr["수리후사용"] + repair_mid + visit_fee`
> - 구독전환 = `sub_monthly × 60 + elec_5yr["신형"]`
> - 신제품구매 = `purchase_mid + elec_5yr["신형"]`
>
> 여기서 `elec_5yr[*]`는 연도별 효율감퇴 시퀀스(1~5년차)를 반영한 5년 전기비 합산이다(`_calc_5yr_elec` — app/backend / `calc_yearly_elec` — project/demo_calculation_5yr.py).
>
> ※ **출처 경로 안내**: 본 문서가 인용하는 `app/backend/app/services/calculation.py`는 **저장소 루트**의 FastAPI 구현(현 `project/`의 상위 폴더)이며, 동일한 5년 로직의 Streamlit 구현은 `project/demo_calculation_5yr.py`·`project/pages/3_Option_Comparison.py`에 있다. (두 구현체의 값은 일치)
>
> ⚠ **코드 식별자 주의**: `OptionScoreV2`의 비용 필드명은 아직 `three_year_cost`(과거 3년 명칭)이나 **현재 5년 비용을 담는다**(scoring_v2.py·calculation.py 공통). 5년 마이그레이션 시 rename 대상. [검토 필요: 필드명 정리]
> 효율감퇴 시퀀스: 계속사용=현재효율 유지·매년 −0.025 / 셀프케어=현재효율+0.03 시작 / 수리후사용=0.825 시작 / 신형=1.0 시작, 모두 하한 0.65.

참고 — `src/scoring_v2.py` `build_options`의 단순(효율 미반영) 1차 산식:

### 수리 후 사용: 재수리 기대비용 추가 (보완 로직)

## 4단계: 탄소 영향 계산 (LG ESG 단계별 비율 기반)

### LG ESG 보고서 기반 단계별 탄소 비율 (에어컨)

| 단계 | 비율 |
|------|------|
| 제조 전 (원자재) | 35.6% |
| 제조 | 0.7% |
| 사용 | 62.1% |
| 폐기 | 1.6% |

비사용단계(제조전+제조+폐기) 합계: **37.9%**

### 계산 공식

```
5년 사용단계 탄소(구형) = K_AC_구형_월 × 사용개월 × 5 × 배출계수
5년 사용단계 탄소(신형) = K_AC_신형_월 × 사용개월 × 5 × 배출계수

교체_proxy_탄소 = 신형_5년_사용_탄소 × (37.9% / 62.1%)
                = 신형_5년_사용_탄소 × 0.610

연간 탄소 절감 = (K_AC_구형_월 - K_AC_신형_월) × 사용개월 × 배출계수
탄소 회수기간 = 교체_proxy_탄소 / 연간_탄소_절감  (단위: 년)

수리 proxy 탄소 = 15 kgCO₂ (부품 교체 기준)
배출계수 = 0.4781 kgCO₂/kWh (한국전력 기준)
```

> 비사용단계 비율식 검증: 37.9% / 62.1% = 0.6103 → 약 **0.610**. (코드 `src/scoring_v2.py` `calculate_carbon_summary`의 `non_use_ratio / use`와 일치)
> 사용단계 탄소는 `usage_months × COMPARISON_YEARS(=5)`로 계산한다(코드: `k_ac_*_monthly × usage_months × COMPARISON_YEARS × emission_factor`).

**핵심 주의**:
- 교체가 항상 친환경이 아님
- 탄소 회수기간이 3년 이내면 교체도 탄소 기준 합리적
- 탄소 회수기간이 7년 초과면 수리·셀프케어가 탄소 기준 유리

> ※ '3년 이내'·'7년 초과' 임계값은 비교기간(5년)과 무관한 탄소 의사결정 기준 상수이므로 그대로 유지한다.

## 5단계: 최종 점수 및 가중치

### 기본 공식

```
final_score =
  경제성 × w_economy      (비용 0.80 + 에너지낭비 0.20 합성)
+ 신뢰성 × w_reliability  (점검필요도 개선 반영)
+ 탄소   × w_carbon
+ 편의   × w_comfort      (생활불편도 개선 반영)
+ 초기비용 × w_initial
```

모든 지표는 낮을수록 유리한 방향으로 정규화 후 반전 적용 (0~1).

> **[검토 필요: 경제성 내부식 표기 불일치]** 구버전 문서는 경제성 합성을 **비용 0.70 + 에너지낭비 0.30**으로 표기했으나, 실제 코드(`src/scoring_v2.py` `score_options`)는 **비용 0.80 + 에너지낭비 0.20**(`eco_norm = 0.80*cost + 0.20*waste`)이다. 위 식은 코드 실제값(0.80/0.20)으로 기재했다. (PROJECT.md §7-1 미해결 2번)

### 우선순위 입력 — 비용/환경/편의 3축 점수화 (확정·코드 구현 완료)

우선순위 입력은 기존 6모드 선택에서 **비용/환경/편의 3축 점수화**로 확정 변경됐고, **2026-06-04 결합식 확정 + 코드 구현 완료**다. 우선순위 비중은 **최종 점수의 50%**(`PRIORITY_RATIO = 0.50`), 미응답(3축 합 0) 시 **비용 우선** 폴백. (PROJECT.md §8-2, 코드 `src/scoring_v2.py` `priority_weights_from_axes` / `_resolve_priority`)

**입력**: 분기설문(챗봇)에서 비용 `c` / 환경 `e` / 편의 `v` 각 0~100 점수를 받는다.
(ERD: `diagnosis_session.priority_cost_score / priority_env_score / priority_convenience_score`)

**1) 정규화**
```
total = c + e + v        # 0이면 c=100 (비용 우선 폴백)
p_비용 = c/total,  p_환경 = e/total,  p_편의 = v/total
```

**2) 축 → 5지표 배분** (사용자에게 묻는 축 3개 → 계산 지표 5개)
```
비용 축 → 경제성·초기비용   (축 내 분할 0.70 / 0.30)   ← AXIS_SPLIT_COST
환경 축 → 탄소              (1.00)
편의 축 → 편의·신뢰성       (축 내 분할 0.50 / 0.50)   ← AXIS_SPLIT_CONV
```

**3) 최종 가중치 = 기본 50% + 우선순위 50%** (합은 항상 정확히 1.0)
```
base = {경제성 0.40, 신뢰성 0.20, 탄소 0.15, 편의 0.15, 초기 0.10}   # BASE_WEIGHTS(구 '기본' 모드값)

w_경제성   = 0.5×0.40 + 0.5×(p_비용 × 0.70)
w_초기비용 = 0.5×0.10 + 0.5×(p_비용 × 0.30)
w_탄소     = 0.5×0.15 + 0.5×(p_환경 × 1.00)
w_편의     = 0.5×0.15 + 0.5×(p_편의 × 0.50)
w_신뢰성   = 0.5×0.20 + 0.5×(p_편의 × 0.50)
```

**검산 — "비용 70 / 환경 20 / 편의 10"**

| 지표 | 가중치 |
|------|--------|
| 경제성 | **0.445** |
| 신뢰성 | 0.125 |
| 탄소 | 0.175 |
| 편의 | 0.100 |
| 초기비용 | 0.155 |
| **합** | **1.000** |

→ 비용 중시 사용자에게 경제성이 지배적. 미응답 시 비용=100 → w_경제성 0.55로 자동 폴백.

**하드 룰 연동**: 모드 문자열 대신 **우세 축(dominant axis)**으로 트리거한다. (`_resolve_priority`가 dominant 반환)
- Rule 4(구독 가점): `dominant == "비용"` + 점검 필요도 ≥ 0.50
- Rule 6(탄소 보정): `dominant == "환경"` + 탄소 회수기간 > 7년

**튜닝 손잡이** (모두 코드 상수, 합리적 기본값): `PRIORITY_RATIO=0.50`, `AXIS_SPLIT_COST=(0.70,0.30)`, `AXIS_SPLIT_CONV=(0.50,0.50)`, `BASE_WEIGHTS`.

### (참고) 구 6모드 가중치 — 폐기, 하위호환용 매핑만 보존

> 6모드(기본/비용절감/친환경/초기비용최소/관리편의/오래쓰기)는 **3축으로 대체·폐기**됐다. 단, 기존 데모·시뮬 스크립트가 문자열을 넘기므로 `LEGACY_MODE_AXES`로 **3축 점수에 매핑**해 하위호환을 유지한다(예: 친환경=(0,100,0), 초기비용최소=(100,0,0)). `PRIORITY_WEIGHTS` 6모드 표는 일부 스크립트 참조용으로만 코드에 남겨 둔다. '오래쓰기 ×1.20 보정'은 3축에서 미적용(레거시 문자열에만 잔존).

| 구 6모드 | → 3축 매핑(비용,환경,편의) |
|----------|--------------------------|
| 기본 | (50, 15, 35) |
| 비용절감 | (100, 0, 0) |
| 친환경 | (0, 100, 0) |
| 초기비용최소 | (100, 0, 0) |
| 관리편의 | (0, 0, 100) |
| 오래쓰기 | (20, 30, 50) |

> 베이스 분포·축 내 분할 비율은 MVP 기본값이며, 데이터 검증 후 조정 가능하다.

## 하드 룰 (Hard Rules)

| 룰 | 조건 | 처리 |
|----|------|------|
